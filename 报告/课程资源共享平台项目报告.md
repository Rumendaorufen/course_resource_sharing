# 课程资源共享平台项目报告

## 1. 项目概述

### 1.1 项目背景

随着信息技术的快速发展和教育数字化转型的深入推进，高校教学模式正经历着深刻变革。传统的教学资源管理方式已无法满足现代教学的需求，存在资源分散、共享困难、管理效率低下等问题。为了解决这些问题，提高教学资源的利用率和教学效率，开发一套功能完善、性能优良的课程资源共享平台显得尤为必要。

### 1.2 项目目标

本项目旨在开发一个面向高校的现代化在线教学管理系统，为师生提供便捷的课程管理、资源共享和作业互动解决方案。具体目标包括：

1. 实现教学资源的集中化管理和高效共享
2. 支持多角色权限管理，满足不同用户群体的需求
3. 提供便捷的作业发布、提交和批改功能
4. 实现数据可视化，辅助教学决策
5. 采用先进的技术架构，确保系统的高性能、高可用性和可扩展性
6. 实现MySQL和MongoDB双写机制，提高系统查询性能
7. 构建多级缓存架构，优化系统响应速度

### 1.3 项目范围

本项目主要涵盖以下功能模块：

1. **用户管理模块**：支持管理员、教师、学生三种角色的用户体系，实现完整的注册、登录和认证流程
2. **课程管理模块**：实现课程的创建、编辑、管理和学生名单管理
3. **资源管理模块**：支持多种格式教学资源的上传、下载、分类管理和权限控制
4. **作业管理模块**：实现作业的发布、提交、批改和成绩反馈功能
5. **数据可视化模块**：提供资源分布、作业完成情况等数据统计图表
6. **技术架构优化**：实现MySQL和MongoDB双写机制、多级缓存架构等技术亮点

### 4.2 核心技术亮点

#### 4.2.1 MySQL和MongoDB双写架构

##### 设计目标
- 实现MySQL和MongoDB的数据双写机制
- 确保数据一致性
- 无需引入消息队列，降低系统复杂度
- 支持资源、作业和作业提交数据的双写
- 实现可靠的重试和错误处理机制

##### 核心设计思路
1. 查询MongoDB文档中的数据，必须通过数据库表中保存的mongoId
2. 若mongoId在数据库中未保存成功，MongoDB中的数据永远不会被查询到
3. 新增数据时：先写MongoDB，再写MySQL
4. 修改数据时：新增MongoDB文档，生成新mongoId，再修改MySQL
5. 删除旧MongoDB文档时：直接在业务代码中处理，实现本地重试机制
6. 若本地重试失败，记录日志，由定时任务清理

##### 双写流程

1. **新增资源流程**
   - 生成新的mongoId
   - 写入MongoDB文档
   - 写入数据库表
   - 更新成功返回结果
   - 数据库写入失败，MongoDB数据成为垃圾

2. **修改资源流程**
   - 生成新的mongoId
   - 新增MongoDB文档（不直接修改旧文档）
   - 修改数据库表，更新mongoId
   - 直接删除旧MongoDB文档（带本地重试）
   - 删除成功返回结果
   - 删除失败记录日志，由定时任务清理

3. **定时清理垃圾数据流程**
   - 定时任务触发
   - 查询待清理记录
   - 遍历待清理记录
   - 删除MongoDB文档
   - 更新清理记录状态

##### 技术实现
- **MongoDbService**：提供MongoDB操作的核心服务，包括save和delete方法
- **MongoDbServiceImpl**：实现了带重试机制的文档删除逻辑
- **MongoCleanupJob**：每小时执行一次的定时任务，清理MongoDB垃圾数据
- **mongo_cleanup表**：记录需要清理的MongoDB文档信息

#### 4.2.2 多级缓存架构

##### 设计目标
- 实现Caffeine（一级缓存）+ Redis（二级缓存）的多级缓存架构
- 保证缓存数据一致性
- 提高系统响应速度和并发能力
- 增强系统容错性
- 防止缓存穿透和缓存击穿

##### 架构组成

1. **一级缓存（Caffeine）**
   - 位置：应用进程内
   - 特点：访问速度快（亚毫秒级）、存储热点数据、容量有限
   - 配置：最大容量1000条、过期时间30分钟、初始容量100

2. **二级缓存（Redis）**
   - 位置：独立的Redis服务器
   - 特点：分布式共享、容量大、访问速度较快（毫秒级）、支持持久化
   - 配置：过期时间60分钟、JSON序列化方式、连接池配置

##### 缓存查询流程
1. 查询一级缓存（Caffeine）
2. 若未命中，查询二级缓存（Redis）
3. 若未命中，查询数据库
4. 将结果写入一级和二级缓存

##### 缓存更新流程
1. 更新数据库
2. 更新二级缓存（Redis）
3. 更新一级缓存（Caffeine）
4. Redis写入失败时，仅更新一级缓存，保证数据可用性

##### 容错机制
- Redis不可用时，自动降级到Caffeine缓存
- 记录Redis操作日志，便于监控和排查问题
- 空值缓存机制，防止缓存穿透

## 6. 风险管理与应对措施

### 6.1 风险识别

在项目实施过程中，主要识别了以下风险：

1. **技术风险**：MySQL和MongoDB双写机制实现难度较大，可能影响数据一致性
2. **性能风险**：系统在高并发下可能出现性能瓶颈
3. **安全风险**：系统可能存在安全漏洞，导致数据泄露
4. **进度风险**：需求变更可能导致项目延期

### 6.2 风险应对措施

针对以上风险，采取了相应的应对措施：

1. **技术风险应对**
   - 进行充分的技术调研和方案设计
   - 采用可靠的重试机制和错误处理机制
   - 实现定时清理垃圾数据功能
   - 进行充分的测试验证

2. **性能风险应对**
   - 实现多级缓存架构，优化系统响应速度
   - 对数据库进行索引优化
   - 采用异步处理方式，提高系统并发能力
   - 进行性能测试和优化

3. **安全风险应对**
   - 采用Spring Security进行权限控制
   - 实现JWT认证机制
   - 对敏感数据进行加密存储
   - 进行安全性测试和漏洞扫描

4. **进度风险应对**
   - 采用敏捷开发方法，快速响应需求变更
   - 进行详细的进度规划和监控
   - 合理分配资源，确保关键路径任务按时完成
   - 与客户保持密切沟通，及时解决需求变更问题
