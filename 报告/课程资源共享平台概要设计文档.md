# 课程资源共享平台概要设计文档

## 1. 引言

### 1.1 文档目的

本概要设计文档旨在为课程资源共享平台的详细设计和开发提供指导框架。文档详细描述了系统的架构设计、模块划分、数据设计、接口设计、技术选型和非功能需求实现方案，确保开发团队对系统有统一的理解，保证系统的一致性、可靠性和可扩展性。

### 1.2 项目背景

随着高等教育信息化的不断推进，高校对在线教学管理系统的需求日益增长。传统的教学资源管理方式存在资源分散、共享困难、互动性差等问题，难以满足现代教学的需求。为了解决这些问题，开发一套高效、便捷、安全的课程资源共享平台显得尤为重要。

课程资源共享平台是一个面向高校的现代化在线教学管理系统，旨在为师生提供便捷的课程管理、资源共享和作业互动解决方案。平台采用前后端分离架构，支持多角色权限管理，实现了教学资源的集中化管理和高效共享，有效提升了教学效率和学习体验。

### 1.3 项目范围

本项目涵盖以下核心功能模块：

1. **用户管理模块**：用户注册、登录、认证、权限管理
2. **课程管理模块**：课程创建、编辑、管理、学生管理
3. **资源管理模块**：资源上传、下载、分类、搜索、预览
4. **作业管理模块**：作业发布、提交、批改、评分
5. **数据可视化模块**：资源分布、作业完成情况统计

系统采用前后端分离架构，前端基于Vue 3 + Element Plus开发，后端基于Spring Boot + MyBatis-Plus开发，数据库使用MySQL和MongoDB双写存储，缓存采用Caffeine + Redis二级缓存架构。

## 2. 系统架构设计

### 2.1 整体架构概述

课程资源共享平台采用前后端分离的微服务架构，主要分为以下几个层次：

1. **前端应用层**：基于Vue 3 + Element Plus开发，负责用户界面展示和交互
2. **API网关层**：处理请求路由、负载均衡、认证授权等
3. **后端服务层**：基于Spring Boot开发，提供RESTful API服务
4. **数据访问层**：基于MyBatis-Plus和Spring Data MongoDB开发，负责数据持久化
5. **数据库层**：包括MySQL和MongoDB，实现数据双写
6. **缓存层**：包括Caffeine和Redis，实现二级缓存架构
7. **文件存储层**：本地文件系统，用于存储上传的文件资源

### 2.4 核心组件交互流程

#### 2.4.1 用户认证流程

1. 用户通过浏览器访问登录页面
2. 输入用户名和密码，提交登录请求
3. 前端将请求发送到后端AuthController
4. 后端验证用户信息，生成JWT Token
5. 后端将Token返回给前端
6. 前端将Token存储在本地（LocalStorage）
7. 后续请求携带Token进行认证

#### 2.4.2 资源访问流程

1. 前端组件发起资源访问请求
2. 请求拦截器添加JWT Token
3. 后端验证Token和权限
4. 服务层处理业务逻辑
5. 先查询多级缓存（Caffeine → Redis）
6. 若缓存未命中，查询数据库
7. 将结果写入多级缓存
8. 返回处理结果给前端

#### 2.4.3 文件上传流程

1. 前端通过表单或拖放上传文件
2. 前端将文件发送到后端FileController
3. 后端接收文件，生成唯一文件名
4. 将文件存储到本地文件系统
5. 记录文件元数据到数据库
6. 实现MySQL和MongoDB双写
7. 更新相关缓存
8. 返回文件访问URL给前端

#### 2.4.4 双写机制流程

##### 2.4.4.1 新增数据流程

1. 生成新的mongoId
2. 写入MongoDB文档
3. 写入数据库表
4. 更新成功返回结果
5. 数据库写入失败，MongoDB数据成为垃圾

##### 2.4.4.2 修改数据流程

1. 生成新的mongoId
2. 新增MongoDB文档（不直接修改旧文档）
3. 修改数据库表，更新mongoId
4. 直接删除旧MongoDB文档（带本地重试）
5. 删除成功返回结果
6. 删除失败记录日志，由定时任务清理

##### 2.4.4.3 定时清理流程

1. 定时任务触发
2. 查询待清理记录
3. 遍历待清理记录
4. 删除MongoDB文档
5. 更新清理记录状态

## 3. 模块划分与设计

### 3.1 模块划分原则

系统模块划分遵循以下原则：

1. **高内聚**：每个模块负责一个特定的功能领域，模块内部功能紧密相关
2. **低耦合**：模块之间通过接口通信，减少直接依赖
3. **单一职责**：每个模块只负责一个功能领域
4. **可扩展性**：模块设计考虑未来功能扩展
5. **可测试性**：模块设计便于单元测试和集成测试

### 4.2 数据流转与存储策略

#### 4.2.1 数据流转

1. **用户请求**：前端发起请求，携带JWT Token
2. **认证授权**：后端验证Token和权限
3. **业务处理**：后端服务处理业务逻辑
4. **缓存查询**：先查询一级缓存（Caffeine），再查询二级缓存（Redis）
5. **数据库查询**：若缓存未命中，查询MySQL数据库
6. **数据返回**：将结果返回给前端，并写入缓存
7. **数据修改**：修改数据时，先写入MongoDB，再写入MySQL，最后清理缓存

#### 4.2.2 存储策略

1. **结构化数据**：存储在MySQL数据库中
2. **非结构化数据**：存储在MongoDB数据库中，实现与MySQL的双写
3. **热点数据**：存储在Caffeine（一级缓存）中，提高访问速度
4. **分布式数据**：存储在Redis（二级缓存）中，实现分布式共享
5. **文件资源**：存储在本地文件系统中，文件元数据存储在数据库中
6. **日志数据**：存储在本地日志文件中，支持配置输出到ELK等日志系统

#### 4.2.3 双写机制

1. **新增数据**：
   - 生成新的mongoId
   - 写入MongoDB文档
   - 写入MySQL数据库
   - 数据库写入失败，MongoDB数据成为垃圾

2. **修改数据**：
   - 生成新的mongoId
   - 新增MongoDB文档（不直接修改旧文档）
   - 修改MySQL数据库，更新mongoId
   - 删除旧MongoDB文档（带本地重试）
   - 删除失败，记录到清理表，由定时任务清理

3. **删除数据**：
   - 删除MySQL数据库记录
   - 删除MongoDB文档（带本地重试）
   - 删除失败，记录到清理表，由定时任务清理

2. **应用场景**：
   - 热点资源缓存
   - 用户信息缓存
   - 课程信息缓存
   - 作业信息缓存

#### 6.4.3 前后端分离架构

1. **选型理由**：
   - 提高开发效率，前后端并行开发
   - 提高系统的可扩展性，支持多端应用
   - 简化部署，前后端独立部署
   - 提高系统的可维护性，降低耦合度

   - 第三方集成

## 7. 非功能需求设计

### 7.1 性能设计

#### 7.1.1 响应时间优化

1. **二级缓存架构**：
   - Caffeine作为一级缓存，热点数据访问响应时间≤10ms
   - Redis作为二级缓存，分布式数据访问响应时间≤50ms
   - 缓存命中率≥80%

2. **数据库优化**：
   - 合理设计索引，提高查询性能
   - 使用分页查询，减少数据传输量
   - 优化SQL语句，避免全表扫描
   - 数据库连接池配置优化，最大连接数=CPU核心数×2+有效磁盘数

3. **前端优化**：
   - 路由懒加载，减少首屏加载时间
   - 组件按需加载，减少打包体积
   - 图片懒加载，提高页面加载速度
   - 使用CDN加速静态资源访问

#### 7.1.2 并发处理

1. **线程池优化**：
   - 合理配置线程池参数，核心线程数=CPU核心数，最大线程数=CPU核心数×4
   - 使用异步处理非核心业务逻辑
   - 避免线程阻塞，提高线程利用率

2. **数据库并发优化**：
   - 使用乐观锁解决并发冲突
   - 合理设计事务，减少事务范围
   - 使用读写分离，提高并发读写能力

3. **分布式锁**：
   - 使用Redis实现分布式锁，解决分布式环境下的并发问题
   - 锁超时机制，避免死锁

#### 7.1.3 吞吐量优化

1. **API网关**：
   - 实现请求路由和负载均衡
   - 支持限流和熔断
   - 提高系统的吞吐量和可靠性

2. **异步处理**：
   - 使用异步方式处理非实时业务
   - 消息队列（预留），解耦系统，提高吞吐量

3. **横向扩展**：
   - 支持水平扩展，提高系统吞吐量
   - 使用Docker和Kubernetes实现自动扩缩容

### 7.2 安全性设计

#### 7.2.1 认证授权

1. **JWT认证**：
   - 使用HS256算法签名JWT Token
   - Token有效期24小时，支持刷新机制
   - Token包含用户信息和权限，减少数据库查询

2. **基于角色的访问控制**：
   - 细粒度的权限控制，支持接口级权限验证
   - 动态分配和修改角色权限
   - 前端路由权限控制，防止未授权访问

3. **密码安全**：
   - 使用BCrypt加密存储密码
   - 密码强度验证，至少8位，包含大小写字母和数字
   - 支持密码过期和定期更换

#### 7.2.2 数据安全

1. **数据加密**：
   - 敏感数据传输采用HTTPS
   - 敏感数据存储采用加密算法
   - 支持数据脱敏，保护用户隐私

2. **数据备份**：
   - 定期备份数据库，备份策略：
     - 全量备份：每天一次
     - 增量备份：每小时一次
   - 备份数据存储在安全的位置，支持异地备份
   - 定期测试数据恢复，确保备份有效性

3. **数据访问控制**：
   - 基于最小权限原则，限制数据库用户权限
   - 禁止直接访问数据库，通过应用程序访问
   - 记录数据库访问日志，便于审计

#### 7.2.3 防护措施

1. **防止SQL注入**：
   - 使用MyBatis-Plus的参数化查询
   - 输入验证和过滤
   - 禁止直接拼接SQL语句

2. **防止XSS攻击**：
   - 输入验证和过滤
   - 输出编码
   - 使用Content-Security-Policy头

3. **防止CSRF攻击**：
   - 使用JWT Token，无状态认证
   - 验证Origin和Referer头
   - 使用SameSite Cookie属性

4. **防止暴力破解**：
   - 登录失败次数限制，超过次数锁定账号
   - 使用验证码，防止自动化攻击
   - 登录IP限制，防止异地登录

### 7.4 可靠性设计

#### 7.4.1 容错设计

1. **服务降级**：
   - Redis不可用时，自动降级到Caffeine缓存
   - MongoDB不可用时，记录日志，保证MySQL操作正常
   - 非核心服务不可用时，保证核心服务正常运行

2. **重试机制**：
   - MongoDB操作失败时，自动重试（最多3次）
   - 外部API调用失败时，自动重试（最多3次）
   - 重试间隔指数退避，避免雪崩效应

3. **熔断机制**：

2. **日志监控**：

   - 支持配置日志输出到文件或ELK等日志系统

3. **缓存监控**：
   - Caffeine缓存统计，包括命中率、命中率、加载时间等
   - Redis监控，包括连接数、内存使用、命令执行次数等
   - 支持缓存监控告警
